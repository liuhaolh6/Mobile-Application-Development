## 三、关键代码

### 3.1 数据源：三种规模，id 区间严格隔离

```kotlin
object CurriculumData {
    val empty: List<CourseTask> = emptyList()
    val normal: List<CourseTask> = sampleTasks        // 直接复用实验1 的三条

    // id 从 1000 起步而非 1：若也从 1 开始，findTask 会先命中 normal 的同名 id
    val hundred: List<CourseTask> = List(100) { index -> /* id = 1000 + index */ }

    const val HUNDRED_ID_START: Int = 1000

    fun findTask(taskId: Int): CourseTask? =
        (normal + hundred).firstOrNull { it.id == taskId }
}
```

**为什么 id 要隔离**：`findTask` 在 `normal + hundred` 中取 `firstOrNull`，
两组样本一旦 id 重叠，详情页会静默打开错误的任务 —— UI 表现完全正常，
只有断言能发现。这个坑在本次实验中真实触发过（见第五节故障记录）。

### 3.2 目的地常量：模板、参数名、拼装函数同源

```kotlin
object HomeDestination {
    const val ROUTE: String = "lab2/home"
}

object TaskDetailDestination {
    const val ARG_TASK_ID: String = "taskId"
    const val ROUTE: String = "lab2/detail/{$ARG_TASK_ID}"   // 模板引用常量

    fun createRoute(taskId: Int): String = "lab2/detail/$taskId"
}

const val INVALID_TASK_ID: Int = 0
```

三个要素定义在同一处，`ROUTE` 的占位符由 `ARG_TASK_ID` 插值而来，
NavHost 取值也复用同一个常量。若把它们散落在各处手写，
一旦出现「模板写 `{taskId}`、取值写 `"id"`」这类不一致，
编译期毫无提示，只表现为详情页永远拿到 null。

### 3.3 首页：LazyColumn + key，且不持有 NavController

```kotlin
@Composable
fun Lab2HomeScreen(
    tasks: List<CourseTask>,
    onOpenTask: (Int) -> Unit,      // 只上报 id，不含跳转细节
    modifier: Modifier = Modifier
) {
    if (tasks.isEmpty()) {
        EmptyContent()              // 空态与列表互斥，避免空白观感
    } else {
        LazyColumn(...) {
            item { /* 汇总行：共 N 条，已完成 M 条 */ }
            items(items = tasks, key = { it.id }) { task ->   // key 用业务 id
                TaskCard(..., onClick = { onOpenTask(task.id) })
            }
        }
    }
}
```

- **`key = { it.id }` 必须用稳定业务 id**：若退回用下标，
  滚动复用时会张冠李戴（数据与视图错位）。
- **空列表走 `EmptyContent` 分支**：`LazyColumn` 在数据为空时只渲染一片空白，
  用户无法区分「没有数据 / 还在加载 / 渲染失败」。

### 3.4 详情页：只接收 taskId，不接触 NavController

```kotlin
@Composable
fun TaskDetailScreen(taskId: Int, onBack: () -> Unit, modifier: Modifier = Modifier) {
    val task: CourseTask? = CurriculumData.findTask(taskId)

    // 第一行显式展示 id，便于肉眼验收「导航确实带入了正确 taskId」
    Text(text = "任务 id = $taskId")

    if (task == null) {
        Text("未找到 id 为 $taskId 的任务，请返回后重新选择。")   // 中文错误态，不留空白
    } else {
        /* 标题 / 负责人 / 优先级 / 状态 四行明细 */
    }
}
```

页面自行 `findTask` 而不由调用方传整个对象：这样「打开哪条数据」
完全由 id 决定，与首页传参口径一致，也便于用纯 JVM 单测验证映射关系。

### 3.5 TaskCard 点击后由上层导航

```kotlin
// Lab2TaskCard.kt —— 组件完全不知道「点击后要去哪」
@Composable
fun TaskCard(
    title: String, owner: String, completed: Boolean,
    priority: CourseTask.Priority,
    onClick: () -> Unit,          // 没有默认空实现
    modifier: Modifier = Modifier
)
```

对照实验1 的 `TaskCard(onClick: () -> Unit = {})`：实验1 里它是「可选点击」，
实验2 里点击是核心交互，因此**去掉默认值**，让漏传 `onClick` 直接变成编译错误。

### 3.6 NavHost：全实验唯一持有 NavController 的文件

```kotlin
@Composable
fun Lab2NavHost(tasks: List<CourseTask> = CurriculumData.normal, modifier: Modifier = Modifier) {
    val navController = rememberNavController()

    NavHost(navController = navController, startDestination = HomeDestination.ROUTE) {
        composable(route = HomeDestination.ROUTE) {
            Lab2HomeScreen(
                tasks = tasks,
                onOpenTask = { taskId ->                                  // 只有这里知道去哪
                    navController.navigate(TaskDetailDestination.createRoute(taskId))
                }
            )
        }
        composable(
            route = TaskDetailDestination.ROUTE,
            arguments = listOf(navArgument(TaskDetailDestination.ARG_TASK_ID) { type = NavType.IntType })
        ) { backStackEntry ->
            val taskId = backStackEntry.arguments?.getInt(TaskDetailDestination.ARG_TASK_ID)
                ?: INVALID_TASK_ID
            TaskDetailScreen(taskId = taskId, onBack = { navController.popBackStack() })
        }
    }
}
```

把 `NavController` 收敛在这一个文件里，各页面只通过 `onXxx` 回调上报意图。
收益是**页面可独立 Preview、路由逻辑可独立单测**。

## 四、验收点自检

| 验收点 | 结论 | 依据 |
|---|---|---|
| LazyColumn 列表可滚动 | ✅ | `Lab2HomeScreen` 用 `LazyColumn` + `items(key = { it.id })`；100 条数据滚动流畅 |
| 列表为空时有明确空状态 | ✅ | `EmptyContent` 显示「暂无课程任务」+ 操作提示 |
| Home → TaskDetail 能带 taskId 跳转 | ✅ | 点第 2 条卡片，详情页首行显示「任务 id = 2」 |
| TaskCard 不直接访问 NavController | ✅ | 全工程搜索 `NavController` 的**代码引用**仅命中 `Lab2NavHost.kt` |
| 返回可回到首页 | ✅ | `popBackStack()`；顶部返回箭头与系统返回手势均可用 |
| 非法 taskId 有友好提示 | ✅ | 传入 9999 显示「未找到 id 为 9999 的任务」，非空白页 |

## 六、故障记录：现象 → 定位 → 原因 → 修复

### 现象

加入实验2 代码与 `navigation-compose` 依赖后执行 `build.bat testDebugUnitTest`，
**编译全部通过**，但测试阶段 3 个测试类全部报错：

```
CourseTaskTest > initializationError FAILED
    java.lang.ClassNotFoundException: com.example.lab1.CourseTaskTest
Lab2DestinationTest > initializationError FAILED
    java.lang.ClassNotFoundException: com.example.lab1.lab2.Lab2DestinationTest
CurriculumDataTest > initializationError FAILED
    java.lang.ClassNotFoundException: com.example.lab1.lab2.CurriculumDataTest
3 tests completed, 3 failed
```

注意 `CourseTaskTest` 是实验1 就存在且一直通过的类。连它都失败，
说明问题不在新增代码本身。

### 定位

按「先把变量降到最少」的思路逐步排除：

1. 检查编译产物 `app/build/tmp/kotlin-classes/debugUnitTest/` ——
   **三个 `.class` 文件都在**，说明代码编译没问题，是测试进程加载不到；
2. 怀疑是新依赖导致类路径异常，先后移除 `material-icons-extended`、
   `navigation-compose` 再跑 —— **依然失败**；
3. 把我的 `lab2/` 目录整体移出工程，**只留实验1 原始代码且不新增任何依赖**
   （用 `git diff` 确认 `build.gradle.kts` 与 HEAD 一致）—— **仍然失败**，
   报的还是同一个 `CourseTaskTest` 错误；
4. 至此可判定：与本次新增的代码和依赖**无关**，是运行环境问题。

### 原因

本工程位于 `C:\Users\刘浩\projects\lab1-android`，**路径含中文**。
Gradle 启动测试 worker 进程时，会把测试运行时类路径作为命令行参数传给 worker，
在 Windows 下该字符串按本地 ANSI 代码页编码，而 worker 以 UTF-8 解码，
中文路径因此变成乱码，导致 worker 无法在类路径上找到 `.class` 文件。

这解释了为什么**编译阶段正常**（编译在 Gradle 主进程内完成，不经过该参数传递），
只有**测试阶段**失败。

### 修复

为工程建一个纯 ASCII 路径的目录联接（junction），从该路径构建：

```batch
mklink /J C:\lab1-app "C:\Users\刘浩\projects\lab1-android"
```

之后在 `C:\lab1-app` 下执行构建，测试立即全部通过：

```
BUILD SUCCESSFUL
```

`build.bat` 中已针对 `GRADLE_USER_HOME` 与 `TEMP` 做过同类修正
（重定向到 `C:\gradle-home`、`C:\gradle-tmp`），本次是同一根因在
**工程自身路径**上的又一次体现，因此用同样的思路上移到工程目录解决。

> **提交说明**：源码、依赖、Gradle 配置本身没有任何问题，
> 换到 ASCII 路径即可复现成功，故无需为此改动仓库内容。

## 七、实验结束前自问

### 数据在哪里？

在 `CurriculumData`（内存假数据，本实验无持久层）。它提供三组样本与统一的
查找入口 `findTask(id)`。首页拿到的是 `List<CourseTask>`，详情页拿到的是
`taskId` 再自行查找 —— **两页共享同一份数据，但不共享同一个对象引用**，
避免了「详情页改了标题首页不刷新」这类隐患。

### 状态在哪里？

**页面内部状态为零**：`Lab2HomeScreen` 与 `TaskDetailScreen` 都是无状态的，
所有内容由入参决定，事件通过回调抛出。这正是它们能被 Preview 直接渲染、
被单测直接验证的原因。

唯一的真状态是 `NavController` 持有的**返回栈**，它被收敛在 `Lab2NavHost` 内。
（对比实验1：勾选状态在页面内，因为那属于「界面状态」且不涉及持久化。）

### 事件从哪里来、到哪里去？

点击事件的传递链条是单向的：

```
TaskCard.onClick  →  Lab2HomeScreen.onOpenTask(taskId)
                  →  Lab2NavHost: navController.navigate(createRoute(taskId))
                  →  NavHost 按 ROUTE 找到详情页
                  →  TaskDetailScreen(taskId) 自行 findTask 渲染
```

`TaskCard` 只知道「被点了」，`HomeScreen` 只知道「某 id 的任务被选中了」，
**只有 `NavHost` 知道要跳转**。返回同理：详情页抛 `onBack`，
由 NavHost 执行 `popBackStack()`。

### 错误在哪里处理？

分三层：

1. **编译期**：`onClick` 去掉默认值，漏传直接编译失败；
   `NavType.IntType` 保证 taskId 按整型解析；
2. **运行期**：`arguments?.getInt(...)` 取不到时回落到 `INVALID_TASK_ID`，
   而非 `!!` 抛异常；`findTask` 未命中返回 null；
3. **界面层**：`task == null` 时展示中文提示「未找到 id 为 N 的任务」，
   **不留空白页** —— 空白会让人误以为界面卡死。
